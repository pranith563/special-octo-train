1. Model memory basics

For LLM infra, accelerator memory is the first filter. Compute matters only after the model weights, KV cache, activations, batch and runtime buffers fit. For inference, “unquantized” normally means FP16/BF16 weights, not FP32. FP32 50B inference needs roughly 200GB for weights alone and is not a sensible ₹50L target.

Rule of thumb: weight memory = parameters × bytes per parameter FP32 = 4 bytes, FP16/BF16 = 2 bytes, INT8 ≈ 1 byte, INT4 ≈ 0.5 byte + metadata Inference memory ≈ weights + KV cache + runtime buffers Training memory ≈ weights + gradients + optimizer states + activations + temp buffers + framework overhead

2. Fine-tuning, LoRA, quantization and batching

Fine-tuning feasibility depends on what is being trained. LoRA/QLoRA trains a small adapter and can fit on surprisingly small GPUs. Full fine-tuning updates every model weight, so memory rises from “weights only” to weights plus gradients, optimizer state, activations and runtime overhead. That is why “train a 7B model without mixed precision” is a materially harder requirement than “fine-tune a 7B model.”

5.1 vLLM inference memory breakup

vLLM serving capacity is mostly a memory-budgeting problem after the model loads. A practical vLLM deployment reserves a fraction of GPU memory for the engine, model weights, runtime overhead and KV cache. The KV cache is what lets vLLM batch many active requests, but it is also what long context and high concurrency consume first.

vLLM serving memory, simplified: usable GPU memory target ≈ total VRAM × gpu_memory_utilization total serving memory ≈ model weights + runtime overhead + KV cache + safety headroom model weights ≈ parameters × bytes per weight per-GPU weights with tensor parallelism ≈ total weights ÷ tensor_parallel_size KV cache grows with active tokens: KV memory ≈ active tokens × layers × KV heads × head dimension × 2 × bytes where active tokens = sum(prompt tokens + generated tokens still in cache) across active requests

5.2 Long-context KV cache impact per user

Modern LLMs may advertise 128K or 200K context windows, but the full window is not free. Each active user's KV cache grows with the actual prompt tokens plus generated tokens still resident in cache. If a user sends a 20K-token document, the server pays for roughly 20K tokens of KV cache. If a user fills a 200K context window, one request can consume tens of GB of VRAM on modern GQA models.
